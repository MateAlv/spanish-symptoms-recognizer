## Why this differs from the documented 0.752

`tests/README.md:323` records 0.7521 for its best row. The configurations are
not the same, and the differences are now identified rather than guessed:

| | README's 0.752 row | First run here | Second run here |
|---|---|---|---|
| NER model | `gpt-4o-mini` | `claude-opus-5` | `claude-opus-5` |
| Mapping model | `claude-opus-5` | `claude-opus-5` | `claude-opus-5` |
| Parser | `full-text` | `sentences` | `full-text` |
| NER prompt | `gral-ner-prompt` | same (verified identical) | same |
| Metric | micro code F1 | micro code F1 | micro code F1 |
| **Result** | **0.7521** | **0.588** | **0.6759** |

Checked, so they can be ruled out:

- **The metric is the same.** `compare_models.py:316` scores
  `evaluator.global_code_*`, which is the micro-averaged code F1 computed
  here. Not a text-F1 or a per-document average.
- **The prompt is the same.** The module's built-in default
  (`ner_model/model.py:34`) is byte-identical to `PROMPT_NER_GENERAL` once
  whitespace is normalised, which is the prompt the 0.752 row used.

What remains:

- **Parser: worth 0.088.** Re-running with `full-text` to match the benchmark
  moved micro F1 from 0.588 to 0.676 (P 0.451→0.570, R 0.848→0.831, FP 61→37).
  Splitting into sentences costs precision: each sentence is scored on its own,
  so the model re-reports findings it has already seen and loses the context
  that would rule one out.
- **The NER model differs, and the benchmark's is unavailable.** The 0.752 row
  ran NER on `gpt-4o-mini`, which neither CLI can reach. Its own NER F1 on
  that row is only 0.4959 — the configuration wins *despite* weak NER, which
  the README itself flags as counterintuitive. Substituting `claude-opus-5`
  for NER raises recall (0.831 vs 0.5085) and lowers mapping precision.

So the remaining 0.076 is attributable to the NER model, and closing it would
need `gpt-4o-mini` — an API key, not a subscription CLI. **0.676 is the
comparable figure for a configuration we can actually run.**

## The shape of the error is the useful finding

Both runs show the same asymmetry: recall above 0.83, precision well below it.
The module finds nearly everything the gold standard lists, then adds more. The
additions are not noise. From `historia_1` under `sentences` (18 FPs), checked
against the source text:

| Predicted | Gold standard | Reading |
|---|---|---|
| HP:0002293 Alopecia of scalp | HP:0001596 Alopecia | same finding, finer grain |
| HP:0001698 Pericardial effusion | HP:0001701 Pericarditis | related finding |
| HP:0000980 Pallor | — | text says "palidez severa" |
| HP:0001063 Acrocyanosis | — | text says "cianosis distal" |
| HP:0000790 Hematuria | — | present in the text |

The gold standard annotates "palidez severa seguida de cianosis distal" as the
single code HP:0030880 (Raynaud phenomenon). Extracting the two component
findings is defensible clinically and counted as two false positives here.

So the measured precision is a floor, not an estimate. A reviewer would have
to adjudicate each FP to know the real figure.

## What the number can and cannot support

The evaluator compares **sets of codes per document** (`evaluator.py:86`). It
never checks that a code was attached to the right mention, and a duplicated
phenotype cannot be penalised. With 59 gold mentions across 8 documents, two
or three adjudications move F1 by several points.

Usable for ranking configurations against each other. Not sufficient on its own
to justify replacing the incumbent.

## Cost profile

`full-text` costs 331s for 8 histories (~41s each) against 805s for
`sentences` (~100s each): one NER call per document rather than per sentence,
with the per-mention mapping calls unchanged. So the better-scoring parser is
also the cheaper one, and `sentences` has nothing to recommend it here.

This cannot sit in a synchronous browser request, which `docs/LLM_ACCESS.md`
already anticipated.

## What would make this decisive

1. **Score the incumbent on the same 8 histories.** A harness for this is
   committed in the API repo on `eval/incumbent-baseline`
   (`scripts/eval_incumbent.py`), and it is blocked: the pipeline wants
   `qwen2.5:7b` and this box has only `qwen3.5:4b`, which returns zero
   symptoms. Until it runs, 0.676 has nothing to beat.
2. **Adjudicate the false positives.** A clinician marking each FP as correct,
   over-specific, or wrong converts the precision floor into a real number.
   37 FPs at `full-text` is a tractable amount of review.
3. **Decide whether `gpt-4o-mini` for NER is worth an API key**, which is what
   the remaining 0.076 against the README's row appears to cost.
